# 票券核销接口说明

对应的 OpenAPI 文件：[verification-openapi.json](../接口json/verification-openapi.json)。

当前 MVP 提供提交核销请求和运营者查询核销记录两个接口。核销采用一次请求直接返回结果的方式，不额外提供核销前预查询接口。

## 通用业务规则

- 核销人员的 `userId` 和 `venueId` 从 JWT 登录信息获取，前端不能指定核销人或景点。
- `OPERATOR` 和 `STAFF` 可以提交核销；只有 `OPERATOR` 可以查询当前景点全部核销记录。
- 票券所属场次必须属于当前登录账号的景点，其他景点的票码统一按不存在处理。
- `requestNo` 由调用端为每次扫描或确认操作生成，最长 64 个字符，并通过数据库唯一约束保证请求幂等。
- 同一个 `requestNo` 重试时返回原核销结果，不再次更新票券或新增记录。
- 已知票券的成功和失败核销尝试都写入 `verification_record`。
- 票券状态更新和成功记录写入必须处于同一事务中。

## 1. 提交核销请求

```http
POST /operator/verifications
Authorization: Bearer <token>
Content-Type: application/json
```

请求示例：

```json
{
  "requestNo": "VR-20260803-000001",
  "ticketCode": "TK-A8F29X2",
  "deviceNo": "GATE-01"
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `requestNo` | 是 | 本次核销请求唯一编号，最长 64 个字符 |
| `ticketCode` | 是 | 扫描或输入的票码，最长 64 个字符 |
| `deviceNo` | 否 | 模拟闸机或核销终端编号，最长 64 个字符 |

### 成功核销条件

票券必须同时满足：

- 属于当前账号所在景点。
- 当前状态为 `VALID`。
- 当前时间大于等于 `validFrom` 且小于 `validUntil`。

核销成功后：

- 票券状态变为 `USED`，并写入 `ticket.verified_at`。
- 新增一条 `SUCCESS` 核销记录，`failureReason` 为空。
- 返回票券、参观人、票种、景点和场次概要。

成功响应示例：

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {
    "requestNo": "VR-20260803-000001",
    "result": "SUCCESS",
    "verifiedAt": "2026-08-03T09:15:20",
    "ticket": {
      "id": 701,
      "ticketCode": "TK-A8F29X2",
      "status": "USED",
      "venueName": "海湾科技馆",
      "visitorName": "张三",
      "ticketTypeName": "成人票",
      "visitDate": "2026-08-03",
      "startTime": "09:00:00",
      "endTime": "11:00:00"
    }
  }
}
```

### 核销失败处理

对于能够定位且属于当前景点的票券，下列情况返回 HTTP `200`，但业务结果为 `FAILED`，同时记录失败原因：

| 情况 | `failureReason` 示例 |
|---|---|
| 状态为 `USED` | 票券已核销 |
| 状态为 `VOID` | 票券已作废 |
| 状态为 `EXPIRED`，或当前时间已经达到 `validUntil` | 票券已过期 |
| 当前时间早于 `validFrom` | 票券尚未生效 |

失败响应中的 `data.result` 为 `FAILED`，`ticket.status` 保持实际状态。业务失败使用 HTTP `200`，便于核销终端统一展示“本次核销结果”；参数错误、身份错误和资源不存在仍使用对应的 HTTP 错误状态。

票码不存在或不属于当前景点时返回 `NOT_FOUND`。由于当前 `verification_record.ticket_id` 为非空外键，这两类请求无法写入失败记录；如果后续需要审计未知票码扫描，应新增独立审计表或调整表结构。

### 并发与幂等规则

- 核销票券时必须使用带条件的原子更新，例如仅在 `status = VALID` 且当前时间处于有效期内时更新为 `USED`。
- 通过受影响行数判断核销是否取得执行权，避免两台设备同时扫码都成功。
- 成功更新票券后再写成功记录；任一步失败都回滚。
- `requestNo` 已存在时直接返回原记录，不重复核销。
- 如果同一个 `requestNo` 被用于另一张票券，返回 `CONFLICT`，不能把旧结果当作本次票券的结果。

## 2. 分页查询核销记录

```http
GET /operator/verifications?page=1&size=20&ticketCode=TK-A8F29X2&result=FAILED&verificationDate=2026-08-03
Authorization: Bearer <token>
```

该接口用于运营端“核销记录”页面，只允许 `OPERATOR` 访问。

查询参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| `page` | 否 | 页码，默认 `1` |
| `size` | 否 | 每页数量，默认 `20`，最大 `100` |
| `ticketCode` | 否 | 按票码精确查询 |
| `result` | 否 | `SUCCESS` 或 `FAILED` |
| `verificationDate` | 否 | 核销日期 |

业务规则：

- 只查询票券所属场次属于当前运营者景点的核销记录。
- 按核销时间倒序、记录 ID 倒序排列。
- 返回请求号、核销时间、票码、参观人、票种、工作人员、结果、失败原因和设备编号。
- 查询无结果时返回成功响应和空列表。

响应示例：

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {
    "items": [
      {
        "id": 801,
        "requestNo": "VR-20260803-000002",
        "verifiedAt": "2026-08-03T09:18:10",
        "ticketCode": "TK-B11A8K0",
        "visitorName": "陈晓",
        "ticketTypeName": "成人票",
        "verifierId": 31,
        "verifierName": "检票员01",
        "result": "FAILED",
        "failureReason": "票券已核销",
        "deviceNo": "GATE-01"
      }
    ],
    "total": 1,
    "page": 1,
    "size": 20
  }
}
```

## MVP 暂不提供

- 核销前独立查询、人工确认和批量核销接口。
- 撤销核销、补录核销或直接修改票券状态。
- 工作人员查看全景点核销记录；当前只由运营者统一查询。
- 设备管理、离线核销、动态码、防截图和实时统计。
- 未知票码扫描审计。
